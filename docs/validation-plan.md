# 第一版验证方案

状态：设计稿，检查尚未实现、实验尚未运行。所有阈值在首轮实验前冻结。

## 1. 需求验证先于 Agent

核心假设：接入失败主要来自遗漏契约与业务规则；显式证据、执行门禁和有限修正能减少遗漏及人工收尾。

先用这个任务观察通用编码助手如何失败，而不是预设它一定失败。个人开发者作为首个用户，记录阅读资料、写代码、排错、人工确认所花时间及错误类型。结果不能代表普遍市场需求。若首轮证明任务过简单、两组都稳定成功，应增加一个真实有价值的边界任务并重新冻结实验，保留原结果，不只挑失败样本宣传。

## 2. 固定任务 PAYPAL-WEBHOOK-01

默认宿主从零自写，使用 Java、Maven、JUnit 和可控 HTTP stub；具体依赖版本与许可在实现时验证。宿主预置虚构订单、通用事件入口、订单仓储以及已能独立测试的业务状态规则，PayPal 适配部分留空。禁止先写完整答案再当成 Agent 成果。

任务：为单商户、单次全额 capture 场景补齐 PayPal Payments v2 Webhook 适配，调用官方回传验签接口，关联已知订单并映射状态。模型只修改适配包和新增测试目录；不改通用状态规则、验收测试、构建脚本或基线配置。最终路径按真实宿主冻结。

规定业务契约（这些是示例宿主要求，不全部是 PayPal 的要求）：

- 验签成功后才能处理；HTTP 200 本身不等于验签成功。
- `PAYMENT.CAPTURE.PENDING` → PROCESSING，`COMPLETED` → SUCCEEDED，`DECLINED` → FAILED。拒绝把 v1 的 `DENIED` 混用到 v2 的映射表。
- 订单关联字段从 v2 文档核实后冻结，不允许只凭金额或未经确认的自定义字段匹配订单；核对币种、金额、商户与全额 capture 范围。
- 相同 provider + event ID 幂等，去重与订单修改须原子完成；两个不同事件指向同一已成功 capture 也不得重复产生业务副作用。
- 已成功状态不会因迟到 PENDING 回退；互相冲突的终态进入人工检查，不静默覆盖。实现宿主时显式固定状态转换表。
- 验签 `FAILURE`、非法请求或订单核对失败不改变订单；网络超时、限流或服务错误不得伪装成成功。
- 已验签但无关事件可记录并返回 2xx；未知订单、冲突与不支持场景保留问题记录，状态不变。具体 HTTP 策略在测试冻结前写明，避免无意义重投或过早确认。

暂不做退款、部分 capture、多商户、证书下载与自验签、真实资金操作、数据库迁移或完整结账前端。首版不是完整支付渠道。

## 3. 独立验收包

grader 由运行器持有，执行时只挂载到独立检查环境；Agent 不能读写其源码、参考实现或答案。开发期间会看到检查反馈，但不提供实现答案。最终额外变体仅用于最终评分，不反馈到修正循环。公开仓库以后发布 grader 便于复现，运行时限制读取无法消除模型对公开内容的记忆，须在报告中注明。

| 检查组 | 可执行判据 |
| --- | --- |
| 基础 | 编译及已有测试通过，patch 不越界，未禁用测试或硬编码 stub 成功 |
| 契约 | 验签请求七个必需字段及事件对象正确，webhook ID 来自配置；认证、基地址正确 |
| 验证响应 | SUCCESS 才允许更新；FAILURE、缺失或未知状态均拒绝更新 |
| 事件与数据 | 三种 v2 事件映射正确；金额、币种、商户不符，未知订单和畸形 JSON 不更新 |
| 重复与乱序 | 串行及并发重复不产生双重副作用；成功后迟到 pending 不回退；冲突可追踪 |
| HTTP 故障 | 验签 401、429、5xx、超时分别记录，有限重试；失败不改变订单，不产生成功确认 |
| 未覆盖范围 | 无关事件安全忽略；部分 capture、退款等不会被错误当成单次成功 |
| 报告真实性 | 每个检查可关联退出码、日志和产物哈希；未运行不写通过；人工帮助有记录 |

检查自己的有效性：参考实现应全通过；至少用四个故障变体验证会失败，例如 HTTP 200 即成功、pending 覆盖 succeeded、先入去重后失败导致重投丢失、漏币种检查。变体结果在冻结前保存，不作为实验效果。

离线验签检查只验证接口接入契约，stub 不验证密码学真实性。沙箱单列：OAuth 获得访问凭据、创建并批准测试订单、产生真实 capture 事件、HTTPS 投递并回传验证 SUCCESS；篡改事件得到非成功结果。沙箱辅助代码和配置不作为首任务自动生成成果。若账户或网络不满足条件，标记 BLOCKED，不报“完整接入通过”。

## 4. 执行闭环与运行边界

任务状态：CREATED → ANALYZING → PATCHING → CHECKING → SUCCEEDED；检查失败可回到 PATCHING，最多两次修正（含首次最多三次检查）。信息缺失进入 NEEDS_INPUT，保留问题和人工补充后恢复；终态另有 FAILED、TIMED_OUT、CANCELLED。每次转换写入日志，由程序根据检查结果决定成功，不能由模型自行宣布。

初始可配置预算：单次模型请求 90 秒、检查命令 120 秒、任务执行 15 分钟、20 次模型请求。人工等待另计并设置过期时间，不无限挂起。token 与费用上限在供应商确定后冻结；缺失 usage 或价格时记录未知，不填零。

超时或取消停止新调用，终止检查进程树并释放容器；忽略迟到响应对状态的修改。请求已发出不保证供应商停止计费，计入结果。进程崩溃后把中断任务记录为失败并保留产物，首版不自动恢复任意执行点。

外部工具错误和代码错误分开：模型限流/短暂服务错误最多两次退避重试并消耗总预算；无效工具参数记录并允许有限修正；文档无法获取或缺失关键契约时要求人工补充，不编造。基线受同样预算约束。

运行前只导入显式允许的公开宿主文件，不跟随逃逸符号链接，不拷贝 .git 历史、私有配置或环境变量。原仓库只读，patch 应用在新工作区。工具校验规范化路径、大小和修改白名单，读取资料与代码视为不可信数据，其中指令不能扩大工具权限。

文档抓取限制官方域名及重定向，拒绝内网地址与任意 URL；构建检查使用固定命令，不向模型开放任意宿主 shell。执行容器无 Docker socket、无宿主私有目录、无模型凭据，非 root，限制 CPU、内存、进程、时长和网络。预下载依赖后离线执行。需要沙箱凭据的验证单独运行，结果过滤后写报告，不把凭据传给模型。

上下文保存 task contract、代码证据索引、官方资料来源与摘要、当前 diff 和最近失败摘要；按需重新读取，避免全文仓库反复传输。丢弃片段也保留来源索引。JSONL 保存 run ID、工具参数摘要、起止时间、退出码、修正次数、token、费用与错误类型；限制输出长度，过滤凭据，不保存原始认证头。

## 5. 与通用编码助手的公平比较

固定 base commit、任务文本、官方资料版本、模型版本/参数、工具权限、执行环境、grader、时间/调用预算及价格表。两组使用相同模型和等效的读写、构建工具；通用助手可以自行规划、执行测试与修复，不把基线简化成一次问答。它不额外得到 AdapterForge 的证据模板和程序化阶段门禁；这正是待测差异。

若实际产品的模型或配置无法固定，则额外记录产品基线，明确不是能归因于编排的受控实验。不要把不同模型能力造成的差异归给本系统。

做 5 组配对运行，共 10 次，每次新上下文、新工作区；交替运行顺序，记录缓存策略和网络故障。重复只是同一任务上的稳定性，不代表 5 个独立业务案例。冻结正式运行后禁止根据结果调提示词；调参要另开新批次。

| 指标 | 定义 |
| --- | --- |
| 自动正确率 | 全部核心验收通过的运行数 / 总运行数；另报逐检查组通过率，不用平均分掩盖关键错误 |
| 人工修改量 | 自动阶段结束到全部验收通过的人工分钟、修改文件数、净修改行数；记录编辑和补充需求，无法修复也保留 |
| 耗时 | 自动墙钟时间、人工时间与总交付时间；分别给中位数和全部原始值 |
| 调用成本 | usage、模型请求数、按当时价格计算费用；区分供应商实报与估算，含失败、重试、取消和缓存 |

人工修正由同一人用同一验收目标，尽量隐藏结果属于哪组；不能盲评则注明熟悉程度与练习效应。核心结果表须保留失败运行，不只展示最佳一次。只有两组都完成时才比较交付时间；未完成不能因早停显得更快。

结果表初始为 NOT_RUN，禁止填写演示数据冒充实验。每次报告还需包含资料清单、patch 哈希、检查环境版本、人工介入原因。超预算和系统失败都进入分母，环境故障另报并按事先规则配对重跑，不能单方剔除。

判据见 README。如果基线也 5/5 成功，正确率没有改善空间，只能比较人工工作和代价。若有初步改善，可再增加 5 组，并做小型消融（去掉证据模板、去掉修正循环）探索原因；小样本只能给工程信号。
