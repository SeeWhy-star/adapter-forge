# AdapterForge · 接入工坊

面向 Java 后端开发者的第三方服务接入编码 Agent：把一个明确接入需求转成有资料依据的代码差异，并用独立检查验证结果。

状态：2026-10-14 完成第一轮需求收敛和验证设计。尚未实现 Agent、测试宿主或沙箱接入，尚无效果数据。项目名是本地工作名，未核查商标或包名唯一性。

## 第一版服务谁、完成什么

服务正在维护小型 Java 支付后端、需要补齐支付回调接入的个人开发者。第一项固定任务是：在自行编写的 Java 示例宿主中，补齐 PayPal Payments v2 capture 回调处理，包括回传验签接口调用、事件映射、重复与乱序处理、失败路径及测试。

选择这项任务，是因为它衔接支付后端经验，边界比完整支付渠道接入小，也能观察 Agent 是否理解“验签失败不得改变订单”等业务约束。该选择是待实验验证的判断，不代表已验证用户市场需求。

不做真实收款、退款、对账、多租户、任意仓库接入或自动合并。创建订单和买家批准链路仅作为后续沙箱验证的辅助流程，不纳入首个编码任务。支付案例通过后，才能研究第二类 API 案例；不承诺一键接入任意服务。

## 用户输入与交付

输入是一个明确允许处理的个人仓库及固定 base commit、公开官方文档入口、接入需求，以及允许修改的路径和运行预算。用户已确认从零编写公开宿主，使用虚构数据，不使用实习代码。

用户最终看到：

- 需求与代码扩展点清单，每项关键结论关联文档章节或代码路径、行号及版本。
- patch / diff、Agent 新增测试，以及独立验收结果；两类测试分别列出。
- 每次工具调用和修正记录、时间与 token 消耗、失败原因、未解决问题及人工介入记录。
- 明确结论：本地检查通过、沙箱通过、失败或待人工处理；未执行检查标记为未执行。

## 可验证案例

PayPal 的公开资料提供沙箱说明及 Webhook API，适合先做离线契约检查，再做沙箱冒烟验证。但本人的账号、地区条件和网络链路尚未验证。Webhook 模拟事件不能用于回传验签 API 验证；不能用模拟器成功替代真实沙箱证据。[官方资料与核实边界](docs/sources.md)。

本地测试使用自行构造的虚构订单和 HTTP stub。stub 能检查请求字段及故障处理，不能证明 PayPal 接受签名。真实沙箱只在离线检查完成且个人账号条件满足后运行，凭据不进入模型上下文、仓库或报告。

## 最小实现

先采用 Java 单进程 CLI、显式状态机和一个模型适配接口，不先引入 Agent 框架。Java 版本与依赖版本在首个可运行步骤中锁定并验证；Python 仅在确有脚本需求时引入。

| 逻辑模块 | 最小职责 |
| --- | --- |
| Task / Runner | 校验输入、记录状态、预算、超时、取消与人工介入 |
| Evidence / Context | 获取允许的官方页面、搜索宿主代码、保存依据并按需选取上下文 |
| Model / Tools | 结构化工具调用、参数校验、读取文件、产生并应用受限 patch |
| Workspace / Checks | 在隔离副本运行固定构建与测试，根据失败最多修正两次 |
| Report / Evaluation | 输出差异和执行记录，用冻结任务比较通用助手基线 |

这些是一个应用内部的职责划分，不是五个服务。上下文先用结构化证据清单和按需读取，不建向量库。报告先用 Markdown + JSONL，不先做 Web UI。

隔离副本只防止误改原仓库；执行生成代码前要落实无宿主私有目录、无密钥、无特权的容器边界，限制网络、资源与时长。容器可用性尚未检查。执行细节见[验证方案](docs/validation-plan.md)。

## 成功与调整方向

单次任务成功：固定验收检查全部通过、无越界修改、依据可追溯，失败与未运行检查如实呈现。离线成功与沙箱成功分别记录。

首轮效果实验做同一任务的 5 组配对重复，比较正确率、人工修改量、耗时及模型调用成本。目标是假设：至少 4/5 次自动通过全部核心检查，并相较基线提高全通过率至少 20 个百分点，或在正确率不降低时减少人工修正时间中位数至少 30%；同时总耗时和模型成本中位数不超过基线的 1.5 倍。这些是预设工程决策阈值，不是统计显著性结论。

如果没有改善，就公开失败记录并定位原因：若优势只来自需求清单，应优先做接入检查工具；若自动修改反复失败，缩为证据整理与验证助手；若受账户限制，保留离线结果并标记沙箱未验证。不能通过降低验收要求包装结果。

## 后续小步骤

1. **宿主与独立检查**：实现最小 Java 支付宿主，冻结未完成接入的 base commit、任务和验收包。用人工参考实现及故障变体证明检查会抓错，参考答案不进入 Agent 工作区。
2. **无模型执行闭环**：CLI 接受任务，创建受限执行环境，记录检查、超时、取消并输出报告。先证明执行记录真实可重放。
3. **首个模型闭环**：完成资料定位、工具调用、受限修改、一次检查及最多两次修正。新增能力以一条真实运行记录验证。
4. **配对评估与沙箱**：冻结配置后比较基线，报告改善或不足；单独完成沙箱冒烟，不计入离线正确率。
5. **第二案例决策**：只有第一案例有证据价值后，再挑一个确有缺口的模型供应商任务，评估是否需要抽象共用能力。

每步报告新增能力、执行命令、验证结果和局限。第一轮只交付本文及验证设计，没有创建代码框架、安装依赖或运行沙箱。
